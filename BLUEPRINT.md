## 1. Project Overview

### Vision

**4 PLAY** es una red social vertical para la comunidad de tenis y pádel en Colombia, lanzando primero en **Cartagena** y expandiendo al país. Resuelve un problema concreto: **encontrar gente con tu nivel para jugar, reservar la cancha y no quedarte sin partido el sábado.** Mezcla tres productos en uno: matchmaking estilo swipe (basado en nivel y geolocalización), mensajería directa para coordinar partidos, y reserva integrada de canchas en clubes aliados.

Estéticamente, la marca toma el verde de la cancha, el lima de la pelota, y el calor caribeño de Cartagena. Logo geométrico — un "4" con la pelota anidada en el triángulo negativo (lectura doble: número, "for play", 4 jugadores en pádel).

### Goals

- Lanzar MVP funcional en Cartagena para validar product-market fit con ~1.000 jugadores activos
- Path real de escala: arquitectura que soporte expandir a Bogotá/Medellín/Cali sin rewrites
- Monetización desde día 1: suscripción 4 PLAY+ ($20.000 COP/mes) + comisión sobre reservas
- App nativa iOS + Android **y** web companion (landing + perfiles públicos compartibles)
- Calidad production-ready: auth seguro, RLS, observabilidad, CI/CD, tienda apps lista

### Success Metrics (MVP, primeros 90 días post-lanzamiento)

- **DAU/MAU ratio** ≥ 25% (sticky para una red social)
- **Match rate** ≥ 30% (de los swipes que reciben respuesta)
- **Reservas confirmadas** ≥ 200/mes
- **Conversión a 4 PLAY+** ≥ 8% al final del trial de 7 días
- **Crash-free sessions** ≥ 99.5%
- **App Store rating** ≥ 4.5★

### Out of scope (MVP)

- Torneos formales con brackets (post-MVP)
- Sistema de ranking ELO global (post-MVP, primero rating manual + stats)
- Streaming/video de partidos
- Marketplace de equipamiento
- Coach/entrenador booking
- Multi-idioma (solo es-CO en MVP)

### Decisiones explícitas y por qué NO otros

- **¿Por qué no Flutter?** El usuario no lo pidió, RN+Expo tiene mejor TS DX y comparte código con Next.js (Zod schemas, types, lógica).
- **¿Por qué no Firebase?** Firestore no soporta geo queries reales, las security rules son menos expresivas que RLS, y para matchmaking + rankings + queries relacionales Postgres gana.
- **¿Por qué no Stripe?** No opera oficialmente en Colombia para empresas con NIT colombiano. Wompi (Bancolombia) es el equivalente local con suscripciones, PSE, Nequi.
- **¿Por qué no MercadoPago?** Wompi tiene mejor DX para suscripciones recurrentes y respaldo bancario directo (Bancolombia). MercadoPago se puede añadir como segundo gateway en fase 2 si hace falta.
- **¿Por qué no GraphQL/tRPC?** REST simple + Supabase auto-genera la API desde el schema. Para complejidad mayor en futuro se introduce tRPC en `apps/web` sin romper mobile.
- **¿Por qué no Clerk?** Coste a escala + duplicar fuente de verdad de usuarios. Supabase Auth integrado con RLS es más simple.
- **¿Por qué no MongoDB?** Schema flexible sería peor en una red social con relaciones (matches, conversations, bookings, payments) que viven en relacional natural.

## 4. Data Model

```

profiles ──1:N──> player_sports
profiles ──1:N──> swipes (as swiper)
profiles ──1:N──> swipes (as swiped)
```

```sql
-- RPC: nearby profiles
create or replace function nearby_profiles(
  p_lat double precision,
  p_lon double precision,
  p_radius_km double precision default 10,
  p_sport sport default 'tennis',
  p_min_level numeric default 1.0,
  p_max_level numeric default 7.0,
  p_limit int default 50
)
returns table (
  id uuid,
  username text,
  full_name text,
  photos text[],
  neighborhood text,
  level numeric,
  distance_km double precision
) language sql stable as $$
  select
    p.id, p.username, p.full_name, p.photos, p.neighborhood,
    ps.level,
    st_distance(p.location, st_makepoint(p_lon, p_lat)::geography) / 1000 as distance_km
  from profiles p
  join player_sports ps on ps.profile_id = p.id and ps.sport = p_sport
  where p.is_active
    and p.deleted_at is null
    and p.location is not null
    and ps.level between p_min_level and p_max_level
    and st_dwithin(p.location, st_makepoint(p_lon, p_lat)::geography, p_radius_km * 1000)
    and p.id != auth.uid()
    -- exclude already swiped
    and not exists (
      select 1 from swipes s
      where s.swiper_id = auth.uid() and s.swiped_id = p.id
    )
  order by distance_km asc
  limit p_limit;
$$;

-- RPC: nearby venues
create or replace function nearby_venues(
  p_lat double precision,
  p_lon double precision,
  p_radius_km double precision default 10,
  p_sport sport default null,
  p_limit int default 50
)
returns table (
  id uuid,
  slug text,
  name text,
  neighborhood text,
  photos text[],
  distance_km double precision,
  min_price int,
  has_sport boolean

  select
    v.id, v.slug, v.name, v.neighborhood, v.photos,
    st_distance(v.location, st_makepoint(p_lon, p_lat)::geography) / 1000 as distance_km,
    (select min(price_per_hour) from courts c where c.venue_id = v.id and c.is_active) as min_price,
```

```sql
-- Cuando ambos perfiles dan 'like' (o uno 'super'), crear match + conversation
create or replace function on_swipe_like()
returns trigger as $$
declare
  reciprocal swipes%rowtype;
  new_match_id uuid;
begin
  if new.direction in ('like','super') then
    select * into reciprocal
    from swipes
    where swiper_id = new.swiped_id
      and swiped_id = new.swiper_id
      and direction in ('like','super');

    if found then
      insert into matches (profile_a, profile_b, sport)
      values (
        least(new.swiper_id, new.swiped_id),
        greatest(new.swiper_id, new.swiped_id),
        coalesce(new.sport_context, 'tennis')
      )
      on conflict (profile_a, profile_b) do nothing
      returning id into new_match_id;

      if new_match_id is not null then
        insert into conversations (match_id) values (new_match_id);
        -- push notification disparado vía Edge Function (suscripción Realtime a inserts en matches)
      end if;
    end if;
  end if;
  return new;
end;
$$ language plpgsql;

create trigger trg_on_swipe_like after insert on swipes
  for each row execute function on_swipe_like();
```

## 5. API Design

Estrategia: **REST auto-generado por Supabase (PostgREST)** + **RPCs** para queries geo + **Edge Functions** para webhooks Wompi y fan-out de notifs. No hay backend custom — todo pasa por Supabase con RLS como guard.

### Endpoints (vía Supabase client SDK)

| Operación | Acceso | Implementación |
|-----------|--------|---------------|
| Leer perfil propio | Auth | `supabase.from('profiles').select().eq('id', userId).single()` |
| Editar perfil | Auth | `supabase.from('profiles').update({...}).eq('id', userId)` |
| Buscar perfiles cercanos | Auth | `supabase.rpc('nearby_profiles', { p_lat, p_lon, p_radius_km, p_sport, p_min_level, p_max_level })` |
| Hacer swipe | Auth | `supabase.from('swipes').insert({ swiped_id, direction, sport_context })` |
| Listar mis matches | Auth | `supabase.from('matches').select('*, conversations(*)').or(...)` |
| Listar conversación | Auth | `supabase.from('messages').select().eq('conversation_id', id).order('created_at')` |
| Enviar mensaje | Auth | `supabase.from('messages').insert({ conversation_id, body })` |
| Marcar leído | Auth | `supabase.from('messages').update({ read_at }).eq('id', messageId)` |
| Suscripción realtime msgs | Auth | `supabase.channel('msgs:{conversationId}').on('postgres_changes', …).subscribe()` |
| Buscar canchas cerca | Auth | `supabase.rpc('nearby_venues', { p_lat, p_lon, p_radius_km, p_sport })` |
| Crear reserva | Auth | `supabase.from('bookings').insert({...})` (status='pending', luego pago) |
| Mis reservas | Auth | `supabase.from('bookings').select().eq('booker_id', userId)` |
| Estado suscripción | Auth | `supabase.from('subscriptions').select().eq('profile_id', userId).single()` |
| Reportar usuario | Auth | `supabase.from('reports').insert({...})` |
| Subir foto | Auth | `supabase.storage.from('profile-photos').upload(...)` |

### Endpoints HTTP custom (Next.js API + Edge Functions)

| Método | Ruta | Descripción | Auth |
|--------|------|-------------|------|
| POST | `apps/web/api/wompi/checkout` | Crea sesión de cobro Wompi (suscripción o booking) | JWT Supabase |
| POST | `apps/web/api/wompi/webhook` | Recibe eventos Wompi, valida HMAC, actualiza payments | HMAC secret |
| GET | `apps/web/api/og/profile/[id]` | Imagen Open Graph dinámica para perfil compartido | público |
| GET | `apps/web/api/og/venue/[slug]` | OG para venue compartido | público |
| Function | `supabase/functions/wompi-webhook` | Procesamiento async heavy (alternativa a `apps/web/api/wompi/webhook`) | HMAC |
| Function | `supabase/functions/push-fanout` | Trigger cuando se inserta `messages` o `matches`, envía push | service role |
| Function | `supabase/functions/match-resolver` | (Opcional) lógica server complementaria al trigger SQL | service role |

### Convenciones REST (para los endpoints custom Next.js)

**Response shape (consistente):**
```json
// Success
{ "success": true, "data": { ... } }
// Error
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [] } }
```

**Validación:** Zod en cada handler. Schemas en `packages/core/src/schemas/`.

**Status codes:** 200 (ok), 201 (creado), 400 (validación), 401 (no auth), 403 (no autorizado), 404, 409 (conflicto), 429 (rate limit), 500.

```typescript
// apps/web/app/api/wompi/webhook/route.ts (firma esquemática)
//
// 1. Lee header `x-event-checksum` o equivalente Wompi
// 2. Calcula HMAC-SHA256(payload + WOMPI_EVENTS_SECRET) y compara
// 3. Si event.type == 'transaction.updated':
//    - busca payment por wompi_transaction_id
//    - actualiza payment.wompi_status, raw_response
//    - si APPROVED y purpose='subscription': activa subscription, set current_period_*
//    - si APPROVED y purpose='booking': set booking.status='confirmed' y dispara push al booker
//    - si DECLINED: notifica al usuario
// 4. Devuelve 200 rápido para evitar reintentos
```

**Idempotencia obligatoria** — Wompi puede reenviar el mismo evento. Usa `wompi_transaction_id` como llave única.

## 8. Authentication & Authorization

### Flow

1. **Bienvenida → Onboarding** (pantalla 01)
2. **Login / Register** (email + Google + Apple)
3. **Verify email** (Supabase magic link via Resend)
4. **Profile setup wizard** (3 pasos: foto + nombre/edad + deportes/nivel + ubicación)
5. **Permisos** (location, notifications)
6. **Tabs principal** (search/book/chat/profile)

### Apple Sign-In (obligatorio en iOS)

- Apple exige Apple Sign-In en cualquier app iOS que ofrezca otro social login.
- Implementar con `expo-apple-authentication` + intercambio de identity token con Supabase Auth (`supabase.auth.signInWithIdToken({ provider: 'apple', token })`).

### Google Sign-In

- Mobile: `@react-native-google-signin/google-signin` (configurar SHA-1 Android, Bundle ID iOS, OAuth client web).
- Web: provider Google OAuth en Supabase Dashboard.

### Protected routes

**Mobile:** root layout `app/_layout.tsx` lee `supabase.auth.getSession()`, redirige a `/(auth)/onboarding` si no hay sesión.

**Web:** `middleware.ts` chequea sesión y protege `/account`, `/billing`, `/checkout/*`. Marketing y `/p/[username]` son públicos.

### Session management

- Mobile: Supabase persiste tokens en SecureStore (configurar custom adapter en `lib/supabase.ts`).
- Web: cookies httpOnly via `@supabase/ssr`.
- Token refresh: automático por SDK; en 401 forzar logout limpio.

### Roles & permissions

MVP no tiene admin panel — la moderación se hace por SQL directo (tabla `reports` filtrada). En fase 2 se introduce rol `admin` en `profiles.role` y un dashboard básico (puede ser Retool o un panel Next.js separado).

| `admin` (post-MVP) | Bypass RLS vía service role en panel separado |

```markdown
## Architecture
```

## 16. Reglas No Negociables

1. **No desactivar RLS por conveniencia.** Si una query requiere bypass legítimo, va por Edge Function con service role. La service key nunca se expone al cliente.
2. **Geo data en SRID 4326 (WGS84)** consistente en `profiles.location` y `venues.location`. Distancias en metros (PostGIS) → convertir a km en presentación.
3. **Money en centavos** (`int`). Nunca `numeric`/`float` para dinero.
4. **Idempotencia obligatoria en webhook Wompi.** Sin esto, reintentos duplican estados.
5. **Apple Sign-In obligatorio en iOS** si ofreces Google Sign-In (regla App Store).
6. **No IAP en MVP** — suscripciones cobradas en web. Reservas (servicios físicos) sí en mobile vía Wompi.
7. **Privacidad:** location precisa de usuarios solo se usa server-side para queries; al cliente nunca se devuelve `location` raw, solo `distance_km` redondeada.
8. **Soft delete en profiles.** Nunca hard delete — usuarios reportados o que cancelan, `deleted_at = now()` y `is_active = false`.
9. **Schemas Zod son fuente de verdad** de validación. Compartidos cliente y servidor. Si cambia el schema DB, regenerar types y actualizar schemas Zod en el mismo PR.
10. **Idioma del producto:** español Colombia. Identificadores en inglés. Sin spanglish.
11. **Pruebas obligatorias antes de submit a stores:** flujo completo de signup → match → message → booking → pago en cuenta de prueba.
12. **EAS Update solo para JS/assets.** Cualquier cambio de native code (deps con módulos nativos nuevos, permisos) requiere build + review.
13. **Nada que dependa de Stripe.** Wompi es el gateway oficial. Si en el futuro se añade gateway alternativo, va detrás de una abstracción (`packages/core/src/payments/`).
14. **No CSS-in-JS dinámico costoso en mobile.** NativeWind compila estático — usar variantes y no template literals condicionales.
15. **Realtime channels deben unsubscribe en cleanup** del componente. Memory leak garantizado si no.
16. **Fidelidad de diseño es no-negociable.** Si una pantalla queda visualmente distinta a su artboard en `design/screens.jsx` o `design/landing.jsx`, no se considera "hecha". El gate es la auditoría del Step 16.5.

## 19. Motion, Gestos & Haptics

> El diseño es estático; el feel es la mitad del producto. Esto fija la cinemática.

### 19.1 Principios de motion

- **Spring physics, no easing curves.** Usar `react-native-reanimated` v3 con `withSpring({ damping: 18, stiffness: 180 })` por default.
- **Duración:** micro-interacciones 150-250ms; transiciones de pantalla 300-400ms; modales 350ms.
- **No animaciones decorativas** — toda animación debe transmitir información (origen, destino, estado).
- **Respeta `prefersReducedMotion`** — fallback a fade-only.

### 19.2 Swipe deck — gestos y animaciones

**Card top:**
- Drag horizontal con `useAnimatedGestureHandler`. `translationX` mapeado a:
  - `rotate`: interpolado de -10° a +10° en rango ±screenWidth/2
  - `opacity` de tarjeta: 1 hasta umbral, decae después
  - Indicador overlay: aparece "LIKE" lime esquina top-right cuando `translationX > 60`, `NOPE` coral cuando `< -60`. Opacity 0 → 1 en rango 60-150.
- **Threshold de decisión:** `Math.abs(translationX) > screenWidth * 0.35` o velocidad `> 800px/s`.
- **Snap-back** si no pasa threshold: spring back a (0,0).
- **Throw out** si pasa: spring a (±screenWidth*1.5, 0) con `rotate` final ±20°. Duration objetivo ~300ms.
- **Super like** (gesto swipe up): `translationY < -120` → throw up, lime overlay con ⚡ icon.

**Card de atrás:** `scale` interpolado de 0.96 → 1.0 conforme la frontal se va, `opacity` 0.7 → 1.0.

**Botones de acción:** tap = misma animación que gesto correspondiente. Botón super es más prominente (size 68 vs 56).

**Haptics:**
- `Light` impact al cruzar threshold visible (overlay LIKE/NOPE aparece).
- `Medium` impact al confirmar swipe.
- `Heavy` impact + `Notification.Success` al disparar match modal.

### 19.3 Modal "¡Match!" — la animación de la app

Cuando el insert en `matches` confirma reciprocidad, el cliente que completó el like recibe el evento Realtime. Animación:

1. **Backdrop:** ink rgba(14,27,44,0.85) fade-in 200ms.
2. **Heading "¡Match!":** entra con `scale 0 → 1.1 → 1.0` spring (overshoot 10%) 400ms desde el centro.
3. **Avatares:** entran desde lados opuestos (±200px → 0) con spring damping 14, stagger de 80ms. Foto propia primero, luego del match.
4. **Corazón lime entre avatares:** scale 0 → 1.2 → 1.0 spring delayed 400ms.
5. **Confetti:** 30 partículas lime/coral/cream desde el centro con física simple (gravity 600, lifespan 2s). Usar `react-native-reanimated` o `lottie-react-native` con un asset.
6. **Botones:** fade-up 24px → 0 delayed 600ms.

**Haptics:** `Heavy` impact al iniciar + `Success` notification.

### 19.4 Transiciones de pantalla

| Origen → Destino | Transición |
|------------------|------------|
| Tabs entre sí | Fade cross 200ms (no slide, evita confusión de orden) |
| Tab → detail (profile, venue, booking) | Push slide right→left iOS-style (default Expo Router) |
| Cualquier → Modal (paywall, filters, settings) | Slide bottom→top 350ms con backdrop blur fade |
| Modal → close | Reverse |
| Auth → onboarding | Fade 250ms |
| Match modal | Custom (ver 19.3) |

| Evento | Feedback |
|--------|----------|
| Tap en cualquier botón | Scale 0.96 → 1.0 spring 150ms + light haptic |
| Tap en tab activo | Scroll-to-top con bounce |

## 24. Accesibilidad

### 24.1 Contrast

- Cualquier texto sobre `cream` (#F4F0E8): usar `ink` (#0E1B2C) → AAA grande, AA pequeño.
- Texto sobre `court`: usar `cream` o `lime` solo en tamaños ≥18px (lime sobre court no pasa AA en tamaño body).
- Texto secundario `ash` (#5C5247) sobre `cream`: AA pasa para 14px+.
- **Lime nunca como color de texto body sobre fondo claro.** Solo como accent en backgrounds oscuros (court, ink) o badges.

### 24.2 Targets touch

- Mínimo 44x44px en mobile, 32x32px en web desktop.
- Spacing mínimo entre targets adyacentes: 8px.

### 24.3 Labels accesibles

- Todos los iconos solos (sin texto) tienen `accessibilityLabel` en español: `<Pressable accessibilityLabel="Filtros">`
- Botones de acción swipe: `Pasar`, `Super like`, `Me gusta` (no descripciones técnicas)
- Imágenes de perfil: `accessibilityLabel="Foto de {nombre}"`
- Headings con role `header` (RN: `accessibilityRole="header"`)

### 24.4 Screen reader support

- Mobile: probar en VoiceOver iOS y TalkBack Android antes de submit.
- Web: aria roles correctos, especialmente en swipe gesture (rol button + descripción).

### 24.5 Reduced motion

- Detectar `prefersReducedMotion` (`useReducedMotion` de Reanimated).
- Si activo: deshabilitar confetti, swipe physics simplificadas (fade instead of throw), modal match sin spring.

### 24.6 Tamaño de fuente del sistema

- Respetar `allowFontScaling` por default. Limitar `maxFontSizeMultiplier={1.4}` en headings display para que no rompan layout.

### 26.3 Deep links

Schema: `4play://` (mobile) y `https://4play.co/...` (web universal links).

| Deep link | Destino mobile | Destino web |
|-----------|----------------|-------------|
| `/p/{username}` | `app/profile/[userId].tsx` (resolviendo username → id) | `apps/web/app/p/[username]/page.tsx` |
| `/v/{slug}` | `app/venue/[venueId].tsx` (resolviendo slug → id) | `apps/web/app/v/[slug]/page.tsx` |
| `/match/{matchId}` | `app/chat/[conversationId]` | redirect a app store si no app instalada |
| `/booking/{bookingId}` | `app/booking/[bookingId].tsx` | requiere auth |
| `/checkout/return?status=...` | webhook handler de Wompi return | igual |

Configurar `apple-app-site-association` y `assetlinks.json` en `apps/web/public/.well-known/`.

### 26.4 Universal share strings

Cuando el usuario comparte un perfil/venue/match desde la app, genera string + URL:

- Compartir perfil propio: `Mírame en 4 PLAY: {URL}`
- Compartir venue: `{Venue} en 4 PLAY · {URL}`
- Compartir invitación a la app: `Únete a 4 PLAY, la app de tenis y pádel en Cartagena. {URL}`

## Apéndice B — Comandos de un solo golpe (cheatsheet builder)

```bash
# Setup inicial
git clone <repo> 4play && cd 4play
pnpm install
cp .env.example .env.local
pnpm supabase link --project-ref <id>
pnpm supabase db push
pnpm supabase gen types typescript --project-id <id> > packages/db/src/database.types.ts

# Dev
pnpm dev                          # web + mobile
pnpm -F web dev                   # solo web
pnpm -F mobile dev                # solo mobile
pnpm supabase functions serve     # edge functions local

# Quality
pnpm lint && pnpm typecheck && pnpm test

# Build mobile
cd apps/mobile
eas build --platform ios --profile preview
eas build --platform android --profile preview
eas submit --platform ios

# Backend deploy
pnpm supabase db push --linked
pnpm supabase functions deploy wompi-webhook
pnpm supabase functions deploy push-fanout
```
